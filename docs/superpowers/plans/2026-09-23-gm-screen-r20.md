# GM Screen (Roll20) Implementation Plan

> **For agentic workers:** REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a GM-owned "GM screen" character (`mode = 'gmscreen'`) to the Dungeon Crawler Carl K-Scaffold sheet. It holds a party-wide floor-end counter and a safehouse flag. Linked Crawlers (`mode = 'pc'`) gate End Floor and Level Up on it. Unlinked Crawlers behave exactly as today.

**Architecture:**
- The design is the approved spec `docs/superpowers/specs/2026-09-23-gm-screen-design.md` (Roll20 part only). It is the source of truth. Where this plan resolves a gap, the resolution is listed in **"Spec resolutions"** below.
- All protocol and gating math is **pure helpers attached to `k`**, unit-tested off-platform through the generated `__tests__/testFramework.js`. These are the TDD seams, as in `_crew.js` and ADR-0009.
- Thin sheetworkers wrap the helpers. Receive handlers are driven in tests through `k.callFunc(name, {attributes, sections}, msg)` with plain attribute objects, and `k.send`, `k.pseudoQuery`, `k.livenessCheck` and `k.extractQueryResult` are stubbed.
- The chat transport (`k.send`, cross-sheet `pseudoQuery`), CSS gating and Roll20 query popups are **live-verify gates**, run through Claude in Chrome.
- There are two messages. `gmRegister` goes Crawler → screen, and `gmState` goes screen → Crawler. `gmState` is the one reply a receive handler may send.

**Tech Stack:** K-Scaffold 2.8.0 (Pug + SCSS + sheetworker JS compiled to one HTML/CSS bundle), vitest, npm, Roll20 sandbox game **DungeonCrawlCarl**, Claude in Chrome (`mcp__claude-in-chrome__*`).

### K-Scaffold facts that bite here
- **One script scope.** Every `source/javascript/*.js` file and every `+module` block is concatenated into one script (`+kscript` in `DungeonCrawlerCarl.pug`).
  - Top-level names already taken include `markSet`, `rollD20`, `selfId`, `connections`, `sameName`, `crewRef`, `STAT_ABBR`, `MODES` and `livenessCheck`.
  - The new `_gmscreen.js` **must not redeclare** any of them. Prefix its top-level identifiers with `gm`.
  - Reach shared helpers through `k`. This plan exports `k.selfId` (from `_crew.js`) and `k.markSet` (from `_skills.pug`).
- **Declared attrs only.** K-Scaffold fetches only attrs declared in Pug (or registered in `varObjects.cascades`) into a worker's `attributes` snapshot. An undeclared attr reads `undefined` live, even though unit tests pass with plain objects. This is the `mana_cost_eff` lesson in `_skills.pug`.
  - Each worker task lists the attrs it reads and writes and names the markup task that declares them.
  - **No worker task has a live acceptance.** The first live gate is Task 8.
- **Silent writes.** Worker writes through the proxy do not fire triggers. Derived values that depend on worker-written attrs are therefore recomputed **inline** wherever their inputs are written. The spec requires this for `gm_floor_available`.
- **The proxy drops no-op writes.** The set trap records a change only when the stringified value differs from what `getAttrs` returned, and `getAttrs` returns the **HTML default** for an attr that was never persisted.
  - So `attributes.floor_end_seq = 0` on a fresh sheet whose default is 0 persists nothing.
  - Where the spec needs an attr to *exist* in the character's store, use raw `setAttrs({...}, {silent:true})` instead of the proxy. Task 5 needs this for the screen opener.
- **Async workers.**
  - `attributes.set()` must be called by hand before and after every `await`.
  - Only `k.startRoll`-based calls are awaited: `k.pseudoQuery`, `k.extractQueryResult` and `k.livenessCheck`.
  - A registered worker must not await in one branch and not in the other; the sandbox loses sync. Follow the `pushCrewStats` pattern: the **registered function stays non-async**, handles the unlinked or sync branch inline, and `return`s the promise of an async helper for the network branch.
- **JSON attrs are native** (`attributes.x = [...]` round-trips), with two proxy quirks. An empty array reads back as `0`, and a hidden `'[]'` default arrives as a string. Re-assign a *copy* after mutating a local array. This plan stores no JSON arrays except the existing `undo_stack` string.

### Roll20 constraints (from project memory; do not rediscover)
- **No `setTimeout`** in sheetworkers. Any "after N seconds" is CSS: the existing `dcc-reveal-a/-b` keyframes in `views/_vehicle.pug`, re-armed by **alternating** a state value (`probe-a` / `probe-b`), because an animation restarts only when its name changes.
- **`k.send` / `k.pseudoQuery` never resolve on a missing character.** Roll20 posts one "No character was found" line to chat.
  - `k.livenessCheck(id)` (`_crew.js`, a `pseudoQuery('@{id|character_name}')`) is **the** liveness probe.
  - Write the pessimistic state first and overwrite it on resolve.
  - Never branch on a `k.send` promise: the generated `send` appends `&{noerror}`, so its resolution means nothing about liveness.
  - Sends are fire-and-forget and never awaited.
- **Players can `k.send` to GM-owned sheets** (user-confirmed). A player's Crawler can therefore register with, and read `@{id|attr}` from, the GM's screen.
- **No dynamic `<select>` options in repeating rows.** The roster is therefore a repeating section with a per-row **On roster** checkbox, and rows are resolved by stored `char_id`.
- **RowID casing.** Sheetworker rowIDs (in `sections` arrays, trigger names and worker-written keys) are **lowercase**. `data-reprowid` and `removedInfo` keys are full-cased.
  - Compare rowIDs case-insensitively at that boundary.
  - This plan also compares **character ids** (`char_id`, `screen_id`, `gm_screen_id`) case-insensitively and trimmed, via `k.gmSameId`.
- **DevTools breakpoints stall workers.** If a live sheet shows no derived attrs and inert buttons, ask whether breakpoints are set before bisecting.

### Spec resolutions (gaps this plan closes; each is also listed in the handoff report)
1. **Fail-closed scope.** "Linked" requires `gm_rostered`.
   - A typo'd or never-answered `gm_screen_id` therefore behaves **unlinked** (fail open), exactly as the spec's definition implies.
   - Fail-closed applies only to a Crawler that *was* rostered and whose screen then became unreachable.
   - A Settings status line (`gm_configured` / `gm_linked`) shows "Not on the GM's roster" vs "Linked", so a typo is visible.
2. **Baselines happen only on a `rostered:true` message**, when either `gm_rostered` was false or `screen_id` ≠ `gm_linked_screen`. A `rostered:false` message only stores the flags.
3. **Screen row lag after On roster.** Receive handlers can't send, so the Crawler can't re-register after being baselined. When the GM ticks On roster, the screen therefore **optimistically mirrors the baseline** on that row (`floor_end_done = floor_end_seq`, `available = 0`). The next `gmRegister` corrects it.
4. **Undo End Floor guard wording.** A freshly baselined Crawler has cursor == seq, so it blocks Undo too. This is correct by the spec's rule (undoing would absorb its next floor end). The warning therefore says "at the latest floor end", not "consumed".
5. **Remove control.** It is a per-row action worker that calls `.remove()` on the row. If the row was On roster, it first sends `gmState {rostered:false}` so the Crawler's gates lift. This is a user action, not a receive handler, so the send is allowed. A removed Crawler re-registers, un-rostered, on its next open. The native Modify/delete control is hidden on this fieldset only. A fieldset remove trigger (`gmRowRemoved`, reading full-cased `removedInfo` keys case-insensitively) backs this up, so a native delete can't strand a gated Crawler either.
6. **Screen End Floor confirmation** is a Roll20 roll query via `k.extractQueryResult` (`?{End the floor for: A · B?|No|Yes}`).
   - Names are sanitized: `| { } [ ] , @ % &` are stripped, and names are joined with ` · `. `extractQueryResult` wraps the query as `[[0[response=?{…}]]]`, so brackets break it, and `@` / `%` / `&` would be parsed as attribute, ability or macro syntax.
   - **Nothing is written before that await.** A dismissed query may never resolve, and any flag set first would stick.
7. **Row "available".** The spec's row lists "floor ends still available" but its field list omits it. This plan adds a derived `available` row field (`max(0, seq − floor_end_done)`), shown only when On roster.
8. **"Tooltips".** Roll20 `title` can't bind to an attr, so the End Floor waiting / available (N) texts, Level Up reason texts and the unreachable note are CSS-gated spans in a status line under the header actions. Static `title`s stay on the buttons.
9. **Level Up is not CSS-disabled.** It shows reason spans from the *cached* `gm_safehouse`, but the click always does the live `@{screen|safehouse}` read (spec). A stale cache can therefore never lock a player out. End Floor *is* CSS-disabled when linked with `gm_floor_available = 0`, per the spec.
10. **Id comparisons** (`screen_id` vs `gm_screen_id`, `char_id` vs row `char_id` or `character_id`) are trimmed and case-insensitive. `gm_screen_id` is written back trimmed by its change worker.
11. **Re-register triggers** are the spec's: open, `gm_screen_id` change, and after End Session / End Floor / Level Up / Undo. This is refined to **"only when the action changed state"**, so a refused End Floor or Level Up, or an Undo on an empty stack, never registers (Task 7). A manual edit of `floor` or of pending levels shows on the screen at the next registration.
13. **Double-click guard by construction.** `gm_floor_busy` holds a per-click token, and after the await only the worker whose token is still persisted advances (Task 7). The spec's plain flag can't detect two workers that read before either write lands.
14. **Derived values are written for every non-gmscreen mode,** so a Crawler switched to mob or vehicle drops its gates and badge.
15. **Visibility gap (documented, not fixed).** A Crawler that edits `gm_screen_id` unlinks itself at once, but the screen row still shows On roster until the GM looks at it. Receive handlers can't send, and the Crawler never tells the old screen. ADR-0012 records this.
12. **A `gmscreen` sheet can't crew.** `crewRegister` ignores it, and `pushCrewStats` / `syncCrewingOnOpen` skip it, the same as for vehicles.
16. **Same-screen id edit.** An edit that trims or case-folds to the currently linked screen is a no-op (keeps floor ends).

### Roll20 limitations that force a deviation from the spec (flagged)
- **R20-L1: the opener's "write if unset" can't use the proxy.** The spec says "an opener worker writes `safehouse` and `floor_end_seq` if they're unset". Through the K-Scaffold proxy, writing the default value is a dropped no-op, so the attrs would never exist and `@{id|floor_end_seq}` would fail. The screen opener therefore persists both with a **raw `setAttrs({safehouse, floor_end_seq}, {silent:true})`** using their current values. The attr names and behaviour are unchanged; only the mechanism differs.
- **R20-L2: the confirm dialog is a roll query** (resolution 6). There is no modal API in sheetworkers.
- **R20-L3: tooltips become spans** (resolution 8). The spec already anticipates this.
